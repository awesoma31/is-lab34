## Цель работы

Провести динамический анализ защищённости веб-приложения OWASP Juice Shop с помощью OWASP ZAP, подтвердить уязвимости вручную и построить модель угроз по методологии STRIDE.

## 1. Стенд и инструменты

Приложение **OWASP Juice Shop** (SPA на Angular, REST API на Node.js/Express, БД SQLite) развёрнуто в Docker:

```bash
docker run -d --name juice -p 3000:3000 bkimminich/juice-shop
```

Динамический анализ выполнен сканером **OWASP ZAP 2.17.0** в режиме full scan (паук + Ajax Spider + активное сканирование). Полный отчёт сканера — `zap/zap-report.html`.

```bash
docker run --rm --network labnet -v "$PWD:/zap/wrk:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-full-scan.py -t http://juice:3000 -r zap-report.html -J zap-report.json
```

![Скриншот 2 — список находок ZAP](zap2.png)

Основные находки:

| # | Находка | Risk | CWE | OWASP Top 10 |
|---|---|---|---|---|
| 1 | Content Security Policy (CSP) Header Not Set | Medium | CWE-693 | A02:2025 — Security Misconfiguration |
| 2 | CORS Misconfiguration | Medium | CWE-942 | A02:2025 — Security Misconfiguration |
| 3 | Cross-Domain Misconfiguration | Medium | CWE-264 | A02:2025 — Security Misconfiguration |
| 4 | Backup File Disclosure | Medium | CWE-530 | A02:2025 — Security Misconfiguration |
| 5 | Bypassing 403 | Medium | CWE-348 | A01:2025 — Broken Access Control |

**Разбор находок:**

1. **CSP Header Not Set** — не задан заголовок `Content-Security-Policy`, браузеру нечем ограничить исполнение внедрённого скрипта. Главный усиливающий фактор для XSS. *Контрмера:* строгая политика `default-src 'self'`, запрет `unsafe-inline`.
2. **CORS Misconfiguration** — сервер разрешает обращения к API со сторонних источников. Вредоносный сайт может читать ответы API от имени жертвы. *Контрмера:* белый список доверенных источников.
3. **Cross-Domain Misconfiguration** — слишком широкая политика междоменного доступа, утечка данных на сторонние домены. *Контрмера:* ограничить разрешённые домены.
4. **Backup File Disclosure** — доступны резервные/служебные файлы, которые могут содержать код и секреты. *Контрмера:* убрать такие файлы из веб-каталога.
5. **Bypassing 403** — ресурсы с ответом `403 Forbidden` удаётся получить обходом (регистр, лишние сегменты пути). *Контрмера:* контроль доступа по нормализованному пути на сервере.

## 4. Моделирование угроз (STRIDE)

### 4.1. Диаграмма потоков данных (DFD)

```
                      ║ TB1 — доверенная граница (интернет → сервер)
                      ║
  ┌──────────┐   F1   ║   ┌──────────────┐    F3    ┌──────────────┐
  │   E1     │────────╫──▶│     P1       │─────────▶│     DS1      │
  │Пользова- │        ║   │  REST API    │          │ База данных  │
  │  тель    │◀───────╫───│  (Express)   │◀─────────│  (SQLite)    │
  │(браузер) │   F2   ║   └──────────────┘    F4    └──────────────┘
  └──────────┘        ║
                      ║
```

| ID | Тип элемента | Описание |
|---|---|---|
| E1 | Внешняя сущность | Пользователь в браузере (недоверенная сторона) |
| P1 | Процесс | REST API Juice Shop (Express): аутентификация, поиск, корзина, админ-функции |
| DS1 | Хранилище данных | SQLite: пользователи, хэши паролей, заказы, товары |
| F1 | Поток данных | HTTP-запрос E1 → P1 (логин, поиск, параметры корзины, JWT) |
| F2 | Поток данных | HTTP-ответ P1 → E1 (HTML/JSON, JWT, Set-Cookie) |
| F3 | Поток данных | SQL-запрос P1 → DS1 |
| F4 | Поток данных | Результат выборки DS1 → P1 |
| TB1 | Доверенная граница | Между интернетом и сервером; её пересекают F1 и F2 |

### 4.2. Анализ по STRIDE (STRIDE-per-element)

Каждый элемент DFD проверяется только на применимые к его типу категории угроз:

| Тип элемента | S | T | R | I | D | E |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| Внешняя сущность (E1) | ✓ | | ✓ | | | |
| Процесс (P1) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Хранилище данных (DS1) | | ✓ | | ✓ | ✓ | |
| Поток данных (F1–F4) | | ✓ | | ✓ | ✓ | |

Угрозы по элементам диаграммы:

| Элемент | STRIDE | Угроза | Пример / находка в Juice Shop |
|---|---|---|---|
| E1 | **S** — Spoofing | Злоумышленник выдаёт себя за другого пользователя | Вход под admin через SQLi в форме логина (п. 3.1), использование похищенного JWT |
| E1 | **R** — Repudiation | Пользователь отрицает выполненные действия | Нет журналирования входов и изменений заказов |
| F1 (пересекает TB1) | **T** — Tampering | Подмена параметров запроса | Изменение цены/количества товара в запросе корзины |
| F1 (пересекает TB1) | **I** — Information Disclosure | Перехват/утечка токена | Кража JWT через XSS (п. 3.2) |
| F1 (пересекает TB1) | **D** — Denial of Service | Флуд запросами | Нет ограничения частоты запросов (rate limiting) |
| F2 (пересекает TB1) | **I** — Information Disclosure | Ответ доступен чужим сайтам / раскрывает лишнее | Широкий CORS (находки ZAP 2, 3), отсутствие CSP (находка ZAP 1) |
| P1 | **S** — Spoofing | Обход аутентификации | SQLi в логине: проверка пароля не выполняется |
| P1 | **T** — Tampering | Внедрение кода через ввод | DOM XSS в поиске (п. 3.2) — нет экранирования вывода |
| P1 | **R** — Repudiation | Действия не связываются с пользователем | Отсутствие аудита админ-операций |
| P1 | **I** — Information Disclosure | Раскрытие служебных данных | Доступ к резервным файлам (находка ZAP 4), подробные сообщения об ошибках |
| P1 | **D** — Denial of Service | Исчерпание ресурсов сервера | «Тяжёлые» запросы поиска без лимитов |
| P1 | **E** — Elevation of Privilege | Доступ к функциям администратора | Обход 403 (находка ZAP 5), доступ к админ-функциям обычным пользователем |
| F3 | **T** — Tampering | Ввод пользователя меняет SQL-запрос | SQL-инъекция: конкатенация строк вместо параметризованных запросов |
| DS1 | **T** — Tampering | Изменение записей в БД | Модификация данных через SQLi |
| DS1 | **I** — Information Disclosure | Утечка содержимого БД | Выгрузка таблицы пользователей через SQLi (UNION) |
| DS1 | **D** — Denial of Service | Блокировка/перегрузка БД | Запросы, выбирающие всю таблицу |
| F4 | **I** — Information Disclosure | В ответ попадают лишние поля | Возврат хэшей паролей вместе с данными пользователя |

**Вывод по модели:** большинство подтверждённых уязвимостей (SQLi, XSS, CORS, отсутствие CSP) сосредоточено на потоках **F1/F2, пересекающих доверенную границу TB1**, и в процессе **P1**, который принимает недоверенный ввод без валидации. Именно там должны стоять основные контрмеры: валидация и экранирование ввода/вывода, параметризованные запросы (F3), CSP и строгий CORS (F2), rate limiting (F1), проверка прав на каждом эндпоинте (P1).

### 4.3. Детальная угроза (Information Disclosure)

Связка **XSS + отсутствие CSP**: внедрённый скрипт исполняется без ограничений (CSP не задан — находка 1), получает данные сессии и отправляет их на внешний сервер, а широкий CORS (находки 2, 3) облегчает обращение к API от имени жертвы. *Контрмеры:* строгая CSP, экранирование вывода, флаги `HttpOnly`/`Secure`/`SameSite`, белый список CORS.

## 6. Рекомендации

1. Внедрить строгую **Content-Security-Policy** — снижает результативность XSS.
2. Перейти на **параметризованные запросы / ORM** и валидацию ввода — закрывает SQLi.
3. Ограничить **CORS** белым списком доверенных доменов.
4. Реализовать **контроль доступа на сервере** и убрать резервные файлы из веб-каталога.
5. Добавить защитные **HTTP-заголовки** (`HttpOnly`, `Secure`, `SameSite`, HSTS) и **ограничение частоты запросов**.
